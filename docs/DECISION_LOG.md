# Architecture and Modeling Decision Log

This document records the 15 architectural and empirical decisions made in designing the Hiver AI support agent.

| # | Decision | Alternatives Considered | Why Chosen | Evidence & Trade-off |
|---|---|---|---|---|
| **1** | **Single-Brand Subsample (SpotifyCares)** | Ingesting all 2.8M rows across all brands | Full dataset is heterogeneous across airlines, retail, and tech; Spotify has high-volume, public technical resolutions. | Much faster iteration (<2 min indexing) with clean, domain-specific intent coherence. |
| **2** | **Brand Selection via Quality & Resolution Rate** | Selecting largest brand by volume (AmazonHelp / AppleSupport) | Amazon/Apple heavily deflect to private DM / phone calls (>80% generic deflection); Spotify public resolution yield is significantly higher. | Reduces generic "Please DM us" noise in the retrieval index. |
| **3** | **Compact 11-Intent Behaviorally-Distinct Taxonomy** | Dozens of fine-grained categories or hierarchical DAG | Fine-grained taxonomies suffer from extreme label confusion and high human annotator variance. | High inter-annotator agreement (kappa > 0.80) and adequate sample support per class. |
| **4** | **Strict 50/50 Calibration vs Locked Test Partition** | Evaluating directly on cross-validation or unpartitioned golden set | Threshold tuning (confidence, margin, retrieval similarity) on the test set produces overly optimistic coverage metrics. | True out-of-sample performance validation; zero data leakage. |
| **5** | **Macro-F1 as Primary Intent Metric** | Raw Accuracy | Accuracy is skewed by dominant intents (e.g. login, playback issues), hiding failures on critical low-frequency intents. | Forces balanced performance across all classes, including security/legal. |
| **6** | **TF-IDF + Logistic Regression Baseline** | Zero-shot LLM or Naive Bayes | Provides an inexpensive, ultra-fast, transparent, and non-trivial baseline with inspectable feature weights. | Establishes a rigorous statistical hurdle that dense embeddings must beat. |
| **7** | **Dense Sentence Embeddings + Linear Classifier** | End-to-end LLM fine-tuning or BERT fine-tuning | Fine-tuning is computationally expensive, prone to catastrophic forgetting, and hard to inspect live in interviews. | Near-instant training (~10s) with 384-d normalized embeddings; excellent few-shot transfer. |
| **8** | **Exact FAISS Cosine Retrieval (`IndexFlatIP`)** | Hosted vector DB (Pinecone, Qdrant, Milvus) | External vector databases add network latency, operational overhead, cost, and server dependency. | Zero-dependency, sub-millisecond local exact search with deterministic repeatability. |
| **9** | **Explicit Rule-Based Escalation Gate** | End-to-end prompt-based "Agent decides to escalate" | LLMs struggle with consistent boundary calibration and often hallucinate over-confidence on ambiguous queries. | 100% deterministic, audit-trail verified safety guarantees on security and legal triggers. |
| **10** | **Low Retrieval Similarity Triggers Escalation** | Always generating even with low similarity | Generating answers without precedent causes the model to guess or hallucinate non-existent features. | Eliminates ungrounded responses when the support database lacks precedent. |
| **11** | **Mandatory Evidence Citations in Agent Output** | Returning raw unstructured text only | Without explicit evidence IDs, human reviewers cannot trace why an answer was generated. | Direct traceability: every auto-handled output links to specific historical pair IDs. |
| **12** | **Cached Fast Evaluation Path (`--fast`)** | Requiring live paid API calls for every evaluation run; treating `--fast` as headline reproduction | Live LLM evaluation is slow/costly and must not silently use MockLLM for submission numbers. | `--fast` = offline smoke (MockLLM, truncated split). `hiver-agent reproduce` = deterministic headline from committed artifacts. Non-fast `evaluate` requires a live API key. |
| **13** | **Joint Coverage & Acceptability Evaluation** | Evaluating coverage in isolation | An agent can achieve 100% accuracy by escalating everything (0% coverage), or 100% coverage by answering recklessly. | Balances operational deflection against customer safety and satisfaction. |
| **14** | **Empirical LLM Judge vs Human Calibration** | Trusting raw LLM judge scores without validation | Automated judges can exhibit verbosity bias and false agreement. | Computed Cohen's kappa and confusion matrix comparing human scores to judge scores. |
| **15** | **CLI-First / Evaluation-First Before Frontend** | Building a Chat UI / Web dashboard early | Take-home assignments prioritize rigorous data handling, evaluation depth, and system explainability over UI sugar. | Clean Typer CLI, headless CI workflows, and rich automated reporting tables. |
